# 旧手机和现用 Windows 盘符：只读核对

这份核对不建立反向代理或新监听，不读取账号、私有脚本、手机业务文件、Windows 保存的连接或基线。对外只记录服务角色、端口和测量条件；原地址、设备序列号、密钥、实际共享路径和设备原始日志不收录。

## 实际使用的是哪套服务

1. Windows 上仍有一个 `rclone mount` 对应现用 `X:`；不是只读，使用 VFS 写缓存。该进程的现有 TCP 对端与 USB 旧机的可见 VPN 地址一致，目的端口是 `8888`。
2. 旧 vivo V2227A（Android 16）可见 Termux 服务、一个由 shell 启动的 Python 进程、Termux:Boot 的开机接收器，以及运行中的 Tailscale 服务。旧机回环和 Windows 侧对同一服务各做一次无凭据 `OPTIONS /`，均返回 `401` Basic challenge 并标识 WsgiDAV。`8888` 显示通配监听；这说明不是只绑定 VPN 地址，**不等于**已经从局域网或开放互联网验证可入站。Android shell 看不到监听持有者详情和私有启动脚本，因此不声称已复原完整启动链路或断电恢复。
3. 同机另有 PhoneNAS 文件服务端 0.4.2 和云盘客户端 0.2.0，读回的已安装 APK 与历史候选摘要匹配。文件服务端未见活动 NasService，`18888`、`18889` 均未监听；它不在 `X:` 的运行路径。Termux:Boot 可能参与旧服务启动，不能视作可卸载的闲置软件。没有发现可证明无依赖、无用户状态的独立调试残留，没有卸载、清数据或删除文件。

## 效率能判断到哪里

- Windows 侧一次认证前响应，TCP 建连约 **63 ms**，建连到首个响应约 **15 ms**。这只是一次 `401`，不读取文件，不能估算持续上传或下载速率。观察到 Tailscale 报告活动直连端点，端点属于私网；还不能据此确认是同一局域网拓扑、每次都是直连，或中继速度。
- 观察到 Python 进程存在、软件走 VFS 写缓存，不说明 CPU、内存或磁盘已经成为瓶颈。Windows 缓存接受写入也不等价于服务器已收到持久完整文件；真实性能试验必须读回服务器文件并独立对比摘要。
- 当前旧入口是明文 WebDAV/Basic，Tailscale 路径本身的加密不改变 HTTP 服务的绑定范围，也不满足 PhoneNAS 云盘客户端的 HTTPS 配对条件。新 Go 服务在隔离环境里的并发和传输成绩，不能归给旧服务。

建议先在独立 HTTPS 普通共享上并行验证，不替换原盘符。用单个大文件和一批小文件分别测同 Wi-Fi、异地直连、异地中继；记录实际路径、连接/首字节、传完与内容核验时间，以及断线恢复。既有目录的切换、真实 `X:` 互传、改绑定或卸载均不是这次只读核对的一部分。见[维护候选验收](ANDROID-ACCEPTANCE.md)。
